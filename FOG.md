# Running on the Niobium Fog

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._

The quiz scores on the Niobium Fog with `./start_local.sh fog`. The other backends (Niobium's simulator, plain CPU) run the same encrypted math on this computer. Switching between them is a configuration change, not a code change.

## What stays exactly the same

- **The quiz** (`data/quiz.json`), the scoring math, and the 12 era profiles.
- **Encryption and decryption.** Keys are generated on this computer when the demo starts, at ring size 2^16, the size the Fog runs. The secret key is never sent to the scoring service or to the Fog, in any mode: `fog submit` runs `era_server` on a job folder that never contains it.
- **The encrypted circuit.** It's the same compiled `era_server` binary with the same `run_circuit()`. `--sim` records the same hollow trace that `fog submit` dispatches, and replays it locally instead.
- **The UI.** The page shows whatever the compute service reports about itself (`services/backends.py`, `describe()`). A test (`tests/test_backends.py`) fails if `web/app.js` ever checks for a specific backend by name.
- **The client and compute services' HTTP API.**

## What changes: one switch

| | Local | On the Fog |
|---|---|---|
| Start the demo | `./start_local.sh sim` | `./start_local.sh fog` |
| Or via env var | `ERA_BACKEND=sim` | `ERA_BACKEND=fog` |
| Which Fog | n/a | `FOG_TARGET=FUNC_SIM` (Fog's hardware-free simulator) or `FOG` (default, the real Fog) |
| Credentials | none | `~/.fog/credentials` from `fog login`, or `FOG_API_TOKEN` |

The `fog` backend runs the documented dispatch, and nothing Fog-specific was invented:

```
fog submit build/era_server <job dir> --hollow --target=$FOG_TARGET
```

`fog submit` asks the Fog for a worker, points the server at it, and runs it. The server's `replay()` executes on the Fog, the still-encrypted result comes back to the compute service, and from there the pipeline is the same as in `--sim`.

## Setting up

1. **Get a Fog account** (only if you don't have one): https://console.niobium.co/request-account
2. **Log in once.** This stores an API key in `~/.fog/credentials`:
   ```bash
   fog login -u <your Niobium console email>
   fog list
   ```
3. **Readiness check.** This contacts nothing. It checks that the `fog` CLI and `nbcc_fhetch_replay` are on PATH, that the key file is present, and that the app is built:
   ```bash
   make fog-ready
   ```
4. **Run the test on the Fog.** `FUNC_SIM` is the Fog's hardware-free target; no flag means the real Fog:
   ```bash
   FOG_TARGET=FUNC_SIM ./run_test.sh
   ./run_test.sh
   ```
   Each prints `PASS` with era flips = 0, the same result `--sim` gives locally.
5. **Run the demo on the Fog:**
   ```bash
   ./start_local.sh fog
   ```
   After a quiz, step 2 of the pipeline view says "Encrypted math ran on **the Niobium Fog**. Fog target …" with the Fog job ID.

Note: `./run_test.sh` with no flag and no API key prints "No Fog API key found, so nothing was dispatched." and exits 0. That is not a pass, so look for the `PASS` line.

## What the page shows for a Fog run

- **The badge.** Step 2 names the Fog and its target, and shows the job ID that `fog submit` prints (`[fog] assigned <id> -> …`). A Fog run also gets a different color badge (`remote: true` in `backends.py`).
- **Transport timing.** The compute service timestamps every line `era_server` and the transport client print, so the result page splits a Fog run into phases: **job queue** (launch until the Fog assigns a worker), **upload** (the transport client's own progress lines, with the byte count), and **remote run plus download** (from "upload complete" until `replay()` returns). The transport client reports upload progress but not when the response starts, so the download is counted inside the remote-run figure. Local backends show transport "n/a", because nothing leaves this computer.
- **The result size.** `run_circuit()` compresses the scores to one RNS tower, so what comes back from the Fog is about half the size of what went up.
- **Latency.** Each quiz is one Fog job, and queue time comes on top of the compute time. If a run takes more than 5 seconds, the page shows "Still working (N s)…".

## Settings

- `FOG_JOB_MAXWAIT`: how long `fog submit` waits for a worker (default 600 s). The compute service gives up after `--timeout` seconds (default 900).
- `FOG_JOB_MODE=batch|persistent` (default batch) is a `fog` CLI setting. The app doesn't depend on it.

## If a Fog step fails: what to ask Niobium for

These messages come from `fog` itself (niobium-client `scripts/fog`):

| Error you see | What it means | What to ask for |
|---|---|---|
| `no Fog API key` (our preflight) | Not logged in on this computer | Nothing to ask. Run `fog login` |
| `POST /jobs/ returned HTTP 401 (unauthorized)` | Key missing, expired or revoked | A working Fog console account. Then run `fog login` again |
| `POST /jobs/ returned HTTP 403 (forbidden)` | Account exists but can't use this target | Access to target `FUNC_SIM` and/or `FOG` |
| `POST /jobs/ returned HTTP 429 (over quota)` | Job quota used up | A higher job quota (every quiz is one job) |
| `job <id> still queued after 600s` | No worker free | Fog capacity or a scheduled slot for the demo. Or raise `FOG_JOB_MAXWAIT` |

## What leaves this computer in Fog mode

In local modes, no quiz data leaves this computer. In Fog mode, the server's recorded trace and its inputs are sent to a Niobium worker. Those are the inputs `era_server` tags for recording (`tag_input` on the query ciphertext and the plaintext era profiles, `tag_keys` for the public rotation keys), plus the crypto context. The public key is not sent. The secret key is never sent, and the Fog never receives answers, trait numbers, scores or the era. As with the local scoring service, it can see data sizes, how long the math took, and when each request happened; in addition, Niobium sees which account submitted each job.

## If code ever does need to change

Only `services/backends.py` (`FogBackend`) should need touching, for example if Niobium changes the `fog submit` flags. Nothing in `web/`, `app/`, `data/`, or `client_service.py` depends on which backend runs. After any change, run `make check`: it runs all local tests with no Fog account needed.
