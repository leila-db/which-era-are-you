# Switching to the Niobium Fog

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._

Right now the quiz runs fully on this computer, with Niobium's simulator (or plain CPU) doing the encrypted math. Moving to the Fog is the **last deployment step**. It is designed to be a configuration change, not a code change.

## What stays exactly the same

- **The quiz** (`data/quiz.json`), the scoring math, and the 12 era profiles.
- **Encryption and decryption.** Keys are generated on this computer when the demo starts, at ring size 2^16, which is the size Niobium documents for the Fog. The secret key is never sent to the scoring service or to the Fog, in any mode: `fog submit` runs `era_server` on a job folder that never contains it.
- **The encrypted circuit.** It's the same compiled `era_server` binary with the same `run_circuit()`. `--sim` records the same kind of hollow trace that `fog submit` would dispatch. Replaying it on the Fog itself has not been verified yet.
- **The UI.** The page shows whatever the compute service reports about itself (`services/backends.py`, `describe()`). A test (`tests/test_backends.py`) fails if `web/app.js` ever checks for a specific backend by name.
- **The client and compute services' HTTP API.**

## What changes: one switch

| | Now (local) | On the Fog |
|---|---|---|
| Start the demo | `./start_local.sh sim` | `./start_local.sh fog` |
| Or via env var | `ERA_BACKEND=sim` | `ERA_BACKEND=fog` |
| Which Fog | n/a | `FOG_TARGET=FUNC_SIM` (Fog's hardware-free simulator) or `FOG` (default, the real Fog) |
| Credentials | none | `~/.fog/credentials` from `fog login`, or `FOG_API_TOKEN` |

The `fog` backend runs the documented dispatch, and nothing Fog-specific was invented:

```
fog submit build/era_server <job dir> --hollow --target=$FOG_TARGET
```

`fog submit` asks the Fog for a worker, points the server at it, and runs it. Per niobium-client's documentation, the server's `replay()` then executes on the Fog and the still-encrypted result comes back to the compute service, after which the pipeline is the same as in `--sim`. This app hasn't run that path yet.

## Checklist for the switch-over day

Each step must pass before you move to the next one.

1. **Get a Fog account** (only if you don't have one): https://console.niobium.co/request-account
2. **Log in once.** This stores an API key in `~/.fog/credentials`:
   ```bash
   fog login -u <your Niobium console email>
   fog list
   ```
3. **Readiness check.** This contacts nothing. It checks that the `fog` CLI and `nbcc_fhetch_replay` are on PATH, that the key file is present, and that the app is built:
   ```bash
   make fog-ready
   ```
4. **Test on the Fog's hardware-free target:**
   ```bash
   FOG_TARGET=FUNC_SIM ./run_test.sh
   ```
   It must print `PASS` with era flips = 0, the same result `--sim` gives today.
5. **Test on the real Fog:**
   ```bash
   ./run_test.sh
   ```
   It must print `PASS`.
6. **Run the demo on the Fog.** Try the simulator target first, then the real one:
   ```bash
   FOG_TARGET=FUNC_SIM ./start_local.sh fog
   ./start_local.sh fog
   ```
   After a quiz, step 2 of the pipeline view should say "Encrypted math ran on **the Niobium Fog**. Fog target …" and show a Fog job ID.
7. Record the results (timings, job IDs, anything surprising) in DECISIONS.md.

Warning: `./run_test.sh` with no flag and no API key prints "No Fog API key found, so nothing was dispatched." and exits 0. That is not a pass, so look for the `PASS` line.

## What has NOT been verified yet (needs Fog access)

Everything below has only been checked offline. Until it has run against a live Fog, don't treat it as proven.

- **The hollow trace is what the Fog gets.** `fog submit era_server <job> --hollow --target=…`: era_server reports its mode as `fog-hollow`, and the compute service logs a WARNING if a backend that must be hollow (sim, fog) ever reports otherwise. Unit-tested offline; not yet seen on a live Fog.
- **A real `fog submit` round trip** from this app. The command line matches niobium-client's docs and is unit-tested, but it has never run against a Fog worker.
- **Fog job-ID display.** The job ID is read from the `[fog] assigned <id> -> …` line that `fog submit` prints (niobium-client `scripts/fog`). If the format differs, only the job-ID label goes missing. The quiz still works.
- **Latency.** Each quiz is one Fog job. Queue time comes on top of the compute time. If a run takes more than 5 seconds, the page shows "Still working (N s)…", so a slow run doesn't look frozen. Timeouts: `fog submit` waits up to `FOG_JOB_MAXWAIT` seconds for a worker (default 600), and the compute service gives up after `--timeout` seconds (default 900).
- **Transport timing.** The result page shows a "transport" time for a Fog run. The compute service timestamps the transport client's own `[fog] upload …` progress lines on stderr, so **upload** is measured. The **download** is not: `nbcc_fhetch_replay` does not report when the worker's response started arriving, so the download is inside the "remote run plus download" figure (from `[fog] upload complete` to era_server's `[server] replay done`). Splitting it out needs one extra stderr line in niobium-client `src/fhetch_transport/client.cpp` (time to first response byte); `FogBackend.timing()` already has a `download_ms` slot for it. Local backends show transport "n/a". The queue figure is launch to `[fog] assigned`.
- **Batch vs persistent jobs.** The `fog` CLI supports `FOG_JOB_MODE=batch|persistent` (default batch). Whether persistent mode would cut per-quiz latency for a live demo is a question for Niobium. The app doesn't depend on it.

## If a Fog step fails: what to ask Niobium for

These messages come from `fog` itself (niobium-client `scripts/fog`):

| Error you see | What it means | What to ask for |
|---|---|---|
| `no Fog API key` (our preflight) | Not logged in on this computer | Nothing to ask. Run `fog login` |
| `POST /jobs/ returned HTTP 401 (unauthorized)` | Key missing, expired or revoked | A working Fog console account. Then run `fog login` again |
| `POST /jobs/ returned HTTP 403 (forbidden)` | Account exists but can't use this target | Access to target `FUNC_SIM` and/or `FOG` |
| `POST /jobs/ returned HTTP 429 (over quota)` | Job quota used up | A higher job quota (every quiz is one job) |
| `job <id> still queued after 600s` | No worker free | Fog capacity or a scheduled slot for the demo. Or raise `FOG_JOB_MAXWAIT` |

## What leaves this computer in Fog mode

In local modes, no quiz data leaves this computer. In Fog mode, the server's recorded trace and its inputs are sent to a Niobium worker. Those are the inputs `era_server` tags for recording (`tag_input` on the query ciphertext and the plaintext era profiles, `tag_keys` for the public rotation keys), plus the crypto context. The public key is not sent. The secret key is never sent, and the Fog never receives answers, trait numbers, scores or the era. As with the local scoring service, it can see data sizes, how long the math took, and when each request happened; in addition, Niobium sees which account submitted each job. What the transport client actually transmits has not been inspected on a live Fog run yet. The page marks a Fog run with a different color badge (`remote: true` in `backends.py`).

## If code ever does need to change

Only `services/backends.py` (`FogBackend`) should need touching, for example if Niobium changes the `fog submit` flags. Nothing in `web/`, `app/`, `data/`, or `client_service.py` depends on which backend runs. After any change, run `make check`: it runs all local tests with no Fog account needed.
